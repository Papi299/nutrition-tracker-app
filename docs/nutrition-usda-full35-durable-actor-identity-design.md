## Options evaluated

1. Login-name fallback would trust a renamed or recreated role without verified continuity. It cannot distinguish a different human assigned the same name and is rejected.
2. Rewriting stored OIDs or forcing PostgreSQL catalog OIDs would invalidate immutable hashes or require unsupported system-catalog manipulation. It is rejected.
3. Durable principals plus separately governed live bindings preserve audit and authority independently. This is selected. A private installation marker distinguishes the active cluster from copied authorization history without requiring superuser control-data functions or volatile restart timestamps.

## Smallest safe model

Four ingestion relations hold immutable principals, immutable binding requests, immutable binding decisions and the current-binding pointer. The principal has a unique independently verified subject commitment and one immutable authority (`operator` or `approver`); the same principal cannot switch authorities to approve its own operation. No credential or enrollment document is stored: only its canonical commitment, governing reference and attributable decisions.

A private singleton cluster marker is generated by the reviewed DDL. It survives ordinary restarts. It is operational authorization context, not portable backup data. The existing approved pipeline replays private DDL and restores only public/ingestion data, so a fresh target retains its own marker. Copied source bindings and pending requests are inactive until a new decision is approved for that marker. Copying the private marker is outside this contract and must be explicitly refused by future Stage 4B qualification; this task does not change the backup pipeline or declare history 47 qualified.

A dedicated NOLOGIN/NOBYPASSRLS identity definer owns only the identity control surface. Two new NOLOGIN authority groups, governor and reviewer, receive only their narrow request/approval RPCs. Neither has members in the migration. Explicitly vetted LOGIN custodians must be provisioned by an existing trusted administrator. Both sessions must be distinct, nonprivileged, mutually exclusive and separate from ingestion operators/approvers and definer roles. No role creation, password change, generic SQL or generic role-management API is provided.

The governor requests an exact principal, dataset/environment, current login/OID/catalog-membership fingerprint, prior binding, evidence commitment and validity window. The independent reviewer confirms the exact canonical request hash. Activation rechecks the actual catalog, cluster marker, evidence, requester continuity and expected prior binding, then appends an immutable decision and advances the pointer under locks. Request retries and decision retries are idempotent. Conflicting changes serialize and stale proposals fail. Revocation is permanent for that principal and denies even completed-receipt access.

The trusted administrators and the two independent custodians are the enrollment trust root. SQL verifies their authenticated sessions and exact attested decision; an opaque evidence hash alone is never authority. Actual subject/credential continuity must be independently verified outside Git before those custodians authorize a real binding. Synthetic tests use synthetic commitments only. Operators, approvers, consumers and service_role cannot enroll or rebind themselves. GUCs, JWT claims, SQL principal-ID arguments and SET ROLE cannot establish identity.

## Operation boundaries

New plan/approval/receipt/event authority contracts have explicit version discriminators. They bind durable operator and approver IDs and the exact original cluster/binding IDs and hashes. Original OIDs and login names remain immutable audit evidence. Scientific candidate, projection, v1 mapping and lifecycle hash domains are unchanged. No already deployed Full35 receipt exists; compatibility with the defective unmerged authority contract is not claimed or silently inferred.

Preparation and approval resolve actual session_user through a valid current binding. Distinct durable principal IDs enforce independent approval even when names differ. New mutations require the exact bindings and cluster marker recorded in the approved plan. Rebinding never makes an old pending/approved operation executable; fresh plans and approvals are required. Existing completed approvals cannot authorize another mutation.

Completed execution retries and receipt reads instead resolve the current verified operator principal, validate the original operation/approval/token and immutable hashes, then return the persisted receipt. They do not compare current OIDs to original audit OIDs or require the old approver to be logged into the new cluster. They append no operation history, change no timestamp, and create no rows or heads. Revoked or stale requester bindings fail closed. Principal/pointer locks serialize authority changes with operation authorization.
